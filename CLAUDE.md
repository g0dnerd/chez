This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Chez is a chess engine written in Zig featuring a TUI for human-vs-AI gameplay. It uses magic bitboards for move generation and negamax search with alpha-beta pruning for AI decision-making.

## Build Commands

```bash
zig build              # Build both executables (outputs to zig-out/bin/)
zig build test         # Run all tests
./zig-out/bin/tui      # Run the chess TUI
./zig-out/bin/precompute  # Regenerate magic bitboard tables (rarely needed)
```

## Architecture

### Core Data Flow

1. **State.zig** holds the board position using bitboards (6 for piece types, 2 for colors) plus a mailbox array for O(1) piece lookup
2. **movegen.zig** generates legal moves using magic bitboard lookups from **moves.zig**
3. **search.zig** uses iterative deepening with PVS (Principal Variation Search) and a transposition table
4. **evaluation.zig** scores positions using material, piece-square tables, pawn structure, and mobility

### Key Modules

- **Bitboard.zig**: Core bit manipulation (64-bit integers representing the 8x8 board). Immutable operations return new values; mutating variants use `Assign` suffix (e.g., `bitOr` vs `bitOrAssign`). Supports polymorphic arguments via `anytype` (accepts Square, u64, or Bitboard).
- **State.zig**: Board state with Zobrist hashing for transposition table. Hash is updated incrementally in `makeMove()`. Contains both bitboard and mailbox representations for efficiency.
- **game.zig**: Type definitions (Square=u6, Piece=u3, Color=u1, Move, CastlingRights), Zobrist key generation, and utilities like `betweenSquares()`.
- **magics.zig** + **moves.zig**: Pre-computed magic bitboard constants and move lookup tables (auto-generated by precompute.zig)
- **main.zig**: TUI game loop - handles FEN input, move parsing, board rendering

### Search Implementation

- **Iterative deepening**: Searches depth 1, then 2, etc. Transposition table persists across iterations for better move ordering.
- **Principal Variation Search (PVS)**: First move searched with full window; remaining moves use null window, re-searching on fail-high.
- **Transposition table**: Fixed 1M entries (~2^20), direct-mapped with depth-based replacement. Stores exact/lower/upper bound flags.
- **Move ordering**: MVV-LVA (Most Valuable Victim - Least Valuable Attacker) for captures, plus promotion bonus.

### Evaluation Components

- **Material**: pawn=100, knight=305, bishop=333, rook=563, queen=950
- **Piece-square tables**: Positional bonuses per piece type and square (separate king table for endgame)
- **Pawn structure**: Passed pawn bonus (scales with rank), doubled pawn penalty
- **Mobility**: Count of legal moves for knights, bishops, rooks (divided by 4)
- **Endgame detection**: Total material < 2500 triggers king endgame table

### Conventions

- Pieces: pawn=0, knight=1, bishop=2, rook=3, queen=4, king=5
- Colors: white=0, black=1 (toggle with `~` operator)
- Squares: 0-63 (a1=0 to h8=63), row-major (file + rank\*8)
- Evaluation scores are always from the current player's perspective (negamax style)
- Checkmate score: 100000

### Code Style

- Use labeled blocks (`blk: { break :blk value; }`) for complex conditional expressions
- Iterators via `iter()` method pattern (see `Bitboard.iter()`, returns nullable on `next()`)
- Tests placed at bottom of each module using `test "description" { ... }`
- Prefer `@intCast`, `@as` for explicit type conversions
- Use `defer` for loop counter increments when iterating piece types
- Constants use SCREAMING_SNAKE_CASE (e.g., `TT_SIZE`), variables use snake_case
