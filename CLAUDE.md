## Project Overview

Chez is a chess engine written in Zig featuring a TUI for human-vs-AI gameplay. It uses magic bitboards for move generation and negamax search with alpha-beta pruning for decision-making.

## Build Commands

```bash
zig build              # Build all executables (outputs to zig-out/bin/)
zig build test         # Run all tests
./zig-out/bin/tui      # Run the chess TUI
./zig-out/bin/precompute  # Regenerate magic bitboard tables (rarely needed)
```

## Architecture

### Core Data Flow

1. **State.zig** holds the board position using bitboards (6 for piece types, 2 for colors) plus a mailbox array for O(1) piece lookup
2. **movegen.zig** generates legal moves using magic bitboard lookups from **generated/moves.zig**
3. **search.zig** uses iterative deepening with PVS (Principal Variation Search) and a transposition table
4. **evaluation.zig** scores positions using tapered evaluation with material, piece-square tables, pawn structure, and mobility

### Key Modules

- **Bitboard.zig**: Core bit manipulation (64-bit integers representing the 8x8 board). Immutable operations return new values; mutating variants use `Assign` suffix (e.g., `bitOr` vs `bitOrAssign`). Supports polymorphic arguments via type argument `T` (accepts `Square`, `u64`, or `Bitboard`).
- **State.zig**: Board state with Zobrist hashing for transposition table. Hash is updated incrementally in `makeMove()`. Contains both bitboard and mailbox representations for efficiency.
- **engine.zig**: Shared type definitions (Move, Color, Direction, GameResult, MagicTableEntry) and re-exports of all submodules.
- **generated/magics.zig** + **generated/moves.zig**: Pre-computed magic bitboard constants and move lookup tables (auto-generated by precompute.zig, do not edit).
- **tui.zig**: TUI game loop - handles FEN input, move parsing, board rendering. Supports `--engine_color`, `--depth`, `--num_threads`, and `--fen` arguments.

### Search Implementation

- **Iterative deepening**: Searches depth 1, then 2, etc. Transposition table persists across iterations for better move ordering.
- **Principal Variation Search (PVS)**: First move searched with full window; remaining moves use null window, re-searching on fail-high.
- **Transposition table**: Lock-free design (Stockfish-style XOR verification). Fixed 1M entries (~2^20), direct-mapped with depth-based replacement. Stores exact/lower/upper bound flags. Scores clamped to i16 range to avoid corrupting mate scores.
- **Move ordering**: MVV-LVA for captures, promotion bonus, killer move heuristic (2 killers per ply).
- **Quiescence search**: Searches only captures until position is quiet. Handles check evasions specially.
- **Null move pruning**: Skips a move to get quick beta cutoff. Adaptive reduction R = 2 + depth/4. Disabled when in check or lacking non-pawn material.
- **Late Move Reductions (LMR)**: Reduces search depth for later moves that are likely worse. Only for quiet moves at depth >= 3, not in check.
- **Check extensions**: Extends search by 1 ply when giving check.
- **Parallel search (Lazy SMP)**: Threads run full iterative deepening independently, sharing only the TT. Up to 16 threads supported. Default is 8 threads.
- **Repetition detection**: Tracks position history via Zobrist hashes. Twofold in search (implies threefold in game), threefold for game-over detection. Respects halfmove clock for lookback limit.

### Evaluation Components (Tapered)

Uses `Score` struct with separate middlegame (mg) and endgame (eg) values, interpolated by game phase.

- **Material**: pawn=100/120, knight=305/290, bishop=333/350, rook=563/575, queen=950/1000
- **Piece-square tables**: Separate MG/EG tables. King PST encourages safety in MG, centralization in EG.
- **Pawn structure**: Passed pawn bonus (scales with rank, larger in EG), doubled pawn penalty, isolated pawn penalty
- **Mobility**: Bonus per legal move for knights, bishops, rooks (scaled by piece type)
- **Bishop pair**: +30/+50 bonus for having two bishops
- **Rook bonuses**: Open file (+25/+15), semi-open file (+15/+10), rook on 7th rank (+20/+40)
- **King safety**: Pawn shield bonus/penalty (MG only)
- **Knight outposts**: Bonus for knights in opponent's half that can't be attacked by pawns (+25/+15 if pawn-defended)
- **Phase calculation**: Based on piece count (knight=1, bishop=1, rook=2, queen=4, max=24)

### Game Over Detection

- **Checkmate**: No legal moves while in check
- **Stalemate**: No legal moves while not in check
- **50-move rule**: halfmove_clock >= 100
- **Threefold repetition**: Same position 3 times (uses PositionHistory)

### Conventions

- Pieces: pawn=0, knight=1, bishop=2, rook=3, queen=4, king=5
- Colors: white=0, black=1 (toggle with `~` operator)
- Squares: 0-63 (a1=0 to h8=63), row-major (file + rank\*8)
- Evaluation scores are always from the current player's perspective (negamax style)
- Checkmate score: 100000

### Code Style

- Use labeled blocks (`blk: { break :blk value; }`) for complex conditional expressions
  - For simpler ternary expressions, use

    ```zig
    const foo = if (bar)
        1
    else
        2;
    ```

    syntax instead.

- Bitboard iterator via `next()` method (see `Bitboard.next()`, returns nullable)
- Tests placed at bottom of each module using `test "description" { ... }`
- Prefer `@intCast`, `@as` for explicit type conversions
- Use `defer` for loop counter increments when iterating piece types
- Constants use snake_case (e.g., `tt_size`, `max_ply`), variables use snake_case too
- Use regular comments (`// Comment`) instead of doc comments (`/// Comment`)
  - Comments -- only on non-obvious functions. Code should be self-documenting
- Inferred error sets (`!T`) are fine -- no need to enumerate unless there's a reason
- Tests: include inline tests for non-trivial logic, skip for simple wrappers/glue

### Common Pitfalls

- **TT score clamping**: Scores stored in TT are clamped to i16 range. Mate scores near +/-100000 may lose precision if not handled carefully.
- **Repetition lookback**: Only look back `halfmove_clock` positions (since last irreversible move). Checking positions too far back is incorrect.
- **En passant pin**: En passant can expose king to horizontal attack by removing two pawns from the same rank. `enPassantExposesKing()` handles this.
- **Null move restrictions**: Don't use null move pruning when in check or when side has only pawns (zugzwang risk).
- **Atomic operations**: TT uses `Atomic(u64)` with `.monotonic` ordering. Data races are benign (just cause cache misses).
